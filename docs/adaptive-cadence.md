# 自适应采集：合并采集 + 最大间隔（设计）

目标：在**不新增上游接口**（已证实不存在批量接口）的前提下，把 31 款 × 147 店的门店监控
从"每轮 4,557 次请求"压到"≤1,764 次"，并让**间隔从固定值变成最大间隔**——由算法在
`[最小间隔, 最大间隔]` 内决定每款实际多久查一次，**保证不漏**。

## 为什么是这两招（都被实测逼出来的）

1. **批量接口不存在**：活主机扫 ~330 路径 + 带 token 复核 + 全网指纹 + 全站 JS 四条证据链，
   结论一致（`/o2o/buy/skus/v1` 是边缘 deny 规则，到不了应用层）。
2. **"线上信号当门"不成立**：`IB7111-005` 线上 `True/MEDIUM` 而我们 147 店在售 **0**；
   `/discover` 与 `product_feed` 都是**线上渠道**（独立库存池），且 feed 不支持按货号过滤。
   → 线上信号**只能"提前"、不能"跳过"**。
3. **能省的只有请求形状**：一次可用性请求可带 **50 个 GTIN（实测硬上限）**，且**跨款式算数**。

## 一、合并采集（把"每款一轮"改成"每店一轮"）

现状：每个任务（1 款）单独派作业 → 每店 1 个请求 → 31 款 × 147 店 = **4,557 次/轮**。

合并后：同一 owner 的**所有到期款**合并成**一次门店扫描**：

```
每店请求数 = ceil( Σ(款_i 的尺码数) / 50 )
31 款 × ~18 尺码 = 558 GTIN/店  →  ceil(558/50) = 12 次/店
总计 = 12 × 147 = 1,764 次/轮（**2.6× 减少**，且 405 抽签的尝试次数同比减少）
```

要点：

- 响应仍按 `skuId` 归属 → 可以准确还原到 (店, 款, 尺码) ✓；
- 价格随可用性响应回来（不再单独发"3 个/批"的补价请求，只补真正缺价的）；
- 事件落库口径不变；**推送仍按任务归属**（每个任务只推自己款号的变化）。

## 二、最大间隔 + 算法（把"固定节奏"改成"预算内的最优节奏"）

任务配置语义变更：

| 字段 | 旧 | 新 |
| --- | --- | --- |
| `cadence_seconds` | 固定间隔 | **最大间隔**（保证：每款至少这么久被查一次）|
| `min_interval_seconds` | — | 最小间隔（默认 `max(30s, 最大间隔/10)`）|

每轮（tick 或每个作业收尾后）按 owner 决策"这一轮扫什么"：

```
candidates = 该 owner 所有款
         （含 last_checked_at、最近 24h 变化次数、线上信号是否变化）

1) 到期强制（不漏的硬约束）：
   forced = { 距上次检查 ≥ 最大间隔 的款 }              ← 无条件进本轮
2) 其余按优先级排序：
   priority = 0.5·(距上次检查 / 最大间隔)                ← 越久越优先
            + 0.3·归一化(最近 24h 变化次数)              ← 爱变的款优先
            + 0.2·(线上信号有变化 ? 1 : 0)              ← 只有"提前"，不"跳过"
3) 预算检查：
   预计请求 = ceil( Σ(选中款尺码数)/50 ) × 门店数 × 1.6（WAF 抽签估算）
   必须 ≤ 本小时剩余额度；超了就按优先级**从低到高裁**，被裁的款下一轮优先补
4) 执行：把选中款的 GTIN 按门店合并成批次（一店 ≤12 请求），落库 → 生成事件 → 按任务推送
```

**保证**：任何款只要"安静"到超过最大间隔，就会进入 `forced` 集合 ✓ 不会因为算优先级而饿死。

## 三、验收口径（可量化）

| 指标 | 目标 |
| --- | --- |
| 单轮请求数 | 31 款 × 147 店：**4,557 → ≤1,764** |
| 单款最大间隔 | ≤ 任务配置的 `cadence_seconds`（对 `observation` 历史做 SQL 校验）|
| 热/冷分布 | 有变化的款实际间隔显著低于安静款（可出分布图）|
| 额度 | 小时内不再触顶（`BUDGET_EXHAUSTED` 归零），冷却次数下降 |
| 事件正确性 | 合并采集前后同一时段的事件数一致（回归对比）|

## 四、实现切分（三步，风险递增）

1. **合并采集**（`scheduler` 派发 + `jobs` 的 plan 构建）：改动集中在"每店一次扫多款"，
   推送仍按任务拆分。**先做这一步**（2.6× 收益、语义不变）。
2. **最大间隔字段 + 到期强制**（`schemas`/`web`/`scheduler`）：保证不漏的前提下放开节奏。
3. **优先级 + 预算裁剪**（`scheduler` 的小型调度器）：用历史变化与线上信号做加权，
   把省下来的额度倾斜给热款。

## 五、实施记录（2026-10-14，第 1 步：合并采集已上线）

落到代码里的合并规则（`scheduler.dispatch_due_tasks`）：

```
合并键 = (账号, cadence_seconds, 门店集合, 尺码集合)   ← 款式取并集，所以"一款一任务"能合
```

为什么这么定：

- **款式不进键**：一次可用性请求带 50 个跨款 GTIN ✓，一款一任务正是要合的形态；
- **门店集合进键**：合并会扩大扫描范围（单店任务并进全店任务 = 多扫店）✗；
- **尺码集合进键**：`size_labels` 是**扫描期过滤器**（`probe.py` 只上报选中尺码）
  → 合了会把没选的尺码也上报 ✗；
- **cadence 进键**：节奏不同的任务合并 → 慢任务被快节奏拖着反复扫 ✗。

### 生产上踩到的坑（重要）

派发抖动（`dispatch_jitter_seconds`，≤ 间隔 10%）原本是**每任务随机**的 ✗：
31 个"1 款 1 任务"的到期时刻被摊开约一分钟 → 调度器每 10 秒轮询一次，
**每次只到一个任务** → 每个任务各自成一个作业 → **合批从未成立**
（线上观察到 05:30:04 / 05:30:54 / 05:31:55 一分钟一个作业）。

修法（三条，缺一不可）：

1. **到期收拢窗口**（`dispatch_merge_window_seconds`）：把"马上到期"的任务提前收进同一轮
   派发，最多提前**半个间隔**（不会明显提前扫）。这一条只负责收拢**历史遗留的错位**。
2. **按间隔网格对齐**（关键）：`next_run_at` = 「间隔网格 + 组偏移」，落在 `(now, now+间隔]`。
   同一 `(间隔, 组偏移)` 的任务不管在哪一刻被派发，下一个到期时刻都落在**同一个瞬间**
   → 错位在一轮内自动收敛，此后每轮都合并（旧的"现在 + 间隔 + 随机抖动"会让错位**永久保留**：
   两个同批任务错开 60 秒，就永远是 60 秒，窗口再大也合不上）。
3. **组偏移**由合并键稳定哈希得到（≤ 间隔的 10%，且 ≤ `dispatch_jitter_seconds`）：
   错峰只发生在**组与组之间**，组内完全同刻。
4. **合并作业接管已排队的单任务作业**：客户节奏（分钟级）比一次 147 店扫描还快，
   每个任务永远"有作业在跑"，只有恰好同时空出来的两三个任务合得起来
   （生产实测：只能成对合并）。所以到期任务若有**未开跑**的排队单任务作业，
   允许并入本轮合并作业，并用条件 UPDATE 把那几个排队作业置为 `CANCELLED`
   （竞态兜底：worker 若刚好租走则不命中，那次扫描照跑完）。只有一个任务、
   且已有排队作业时保留原作业，不重复派发（否则扫描频率翻倍）。

### 验收口径（生产 SQL）

```sql
-- 合并是否成立：n_tasks ≥ 2 的作业数
SELECT count(*) FILTER (WHERE jsonb_array_length(task_ids) >= 2) AS merged,
       count(*) AS all_jobs, max(jsonb_array_length(task_ids)) AS max_tasks
FROM scan_job WHERE created_at > now() - interval '1 hour';

-- 单轮请求数：一轮合并作业的 store 行 × 每店批次数
SELECT total_stores, jsonb_array_length(style_codes) FROM scan_job ORDER BY created_at DESC LIMIT 5;
```

### 连带修的两处（合并作业没有 `task_id` 暴露出来的）
