# 检查频率、账号冷却与失败门店补跑

本文说明 30 秒频率档的真实语义、额度算术、账号级冷却的进入/恢复条件，以及失败门店的
自动补跑规则。配置项见 `apps/api/app/config.py` 与 `.env.example`；实现见
`app/services/{scheduler,jobs,throttle,quota}.py`。

## 频率档的真实语义

- 任务保存的是**目标间隔**：上一轮检查结束后，按所选间隔开始下一轮；上一轮未结束前不会
  叠加新作业（`dispatch_due_tasks` 发现同任务已有排队/运行中的作业时只推进 `next_run_at`）。
- 因此「每 30 秒」的含义是**一轮接一轮连续检查**，实际间隔 ≥ 一轮耗时 + 30 秒。
- 一个作业的成本 ≈ 每店 2–15 次上游事务（尺码表走 test 域不计数；可用性 1 批/40 个 GTIN
  = 1 PUT + 1–3 次轮询 GET；价格按在货尺码 3 个/批）。全量门店一轮通常要数百次事务，
  平台闸（`quota_hourly_cap` 默认 900/小时、`daily_review_budget` 默认 60000/天、
  租户 `daily_review_budget` 默认 5000/天）决定真实节奏，最长约 1–2 轮/小时。
- 改频率只改任务字段：接口 `cadence_seconds ∈ [30, 86400]`；机器人「频率 30秒 到 <任务名>」
  （支持 秒/s/sec、分钟、小时，下限 30 秒）。

## 额度算术（计费口径）

**到达业务层的上游应答**每次扣 1 次：review PUT、每次轮询 GET、401/403/429/5xx 的重试
尝试都各算 1 次。两类尝试**不计费**：

- **405 WAF 挑战**：上游每次请求独立抽签（实测通过率 ~40–60%），重试是平台被迫的额外动作，
  记在客户头上等于按 ~2 倍速率烧额度——这正是"任务一多就限速"的主因；
- **传输层失败**：请求没有到达上游。

计费发生在**应答之后**（`client._call_quota(charge=True)`），发送前只做**不计数预检**
（`charge=False`），所以额度见底时一个请求都不会发出。尺码结构走 `nike_test_api_base`
（test 域），不计费。

三道闸（租户日预算 → 平台日预算 → 平台小时闸）命中即拒绝（`ScanError(BUDGET_EXHAUSTED)`），
并把拒绝原因写进 `QuotaGuard.last_rejection`（worker 日志里可 grep
`quota rejected upstream request (<原因>)`）。

> 效果：以实测 ~50% 挑战率计，同样的额度买到约 **2 倍**真实事务量；可以先用
> `quota_hourly_cap` 保持不变，观察 `platform_hourly_budget` 拒绝是否消失。

## 账号级冷却

冷却属于**账号**（`credential` 行），该账号的所有任务共享；冷却中调度器不派发
（`next_run_at = cooldown_until`），到点自动继续。

### 进入条件

| 触发 | 原因码 `cooldown_reason` | 窗口 |
|---|---|---|
| 租户日预算用完 | `tenant_budget` | 次日 UTC 00:00 + 30s |
| 平台日预算用完 | `platform_daily_budget` | 次日 UTC 00:00 + 30s |
| 平台小时闸命中 | `platform_hourly_budget` | 下一个整点 + 30s |
| 上游 403/429（重试耗尽） | `throttled` | 阶梯 `300,900,1800,3600` 秒 |

- 风控类连续命中按阶梯升级（`cooldown_level`），取 `max(现有 until, now + 阶梯)`；
  额度类不升级。已有更晚的窗口不会被缩短。
- 一个作业命中以上任一情况时**整轮提前结束**：已成功的门店保留，未完成的门店标 `FAILED`
  并带原因码（诊断事件 `SCAN_FAILED`），不再逐店空转。
- **通知**：进入冷却时发一条系统通知（标题「检查已自动降速」，正文含原因与自动继续时刻），
  间隔至少 `throttle_notice_interval_seconds`（默认 8 小时，即 24 小时内最多 3 条）。

### 恢复条件

- 到点后调度器自动派发；若该账号有补跑作业，先执行补跑（见下）。
- 一整轮全部成功（作业 `SUCCEEDED`）只重置 `cooldown_level=0`；`cooldown_until` 只有在过期
  之后才会被清空——其他任务的短暂成功不会提前解除仍在生效的窗口。

### 观测方式

- 数据库：`credential.cooldown_until / cooldown_level / cooldown_reason / cooldown_notified_at`；
  `scan_job.not_before / retry_round`；门店级原因见 `scan_job_store.error_code`（`BUDGET_EXHAUSTED`、
  `THROTTLED`）。
- 接口：任务列表/详情返回 `cooldown_until`、`cooldown_reason`；页面显示「冷却中 · 将在 HH:mm 自动继续」。
- 日志：`nike_mp.throttle`（cooldown entered / notice queued）、`nike_mp.quota`（quota rejected）、
  `nike_mp.jobs`（scheduled retry ...）。

## 失败门店自动补跑

作业结束时（`jobs._finalize`）满足以下**全部**条件才创建补跑作业：

1. 作业属于某个任务，且任务仍启用；
2. 存在 `FAILED/UNKNOWN` 门店，且其 `error_code` 不是凭证类（不以 `NIKE_` 开头、不是 `AUTH_REQUIRED`）；
3. `job.retry_round < job_max_attempts`（默认 3，原作业为第 0 轮）；
4. 该任务没有其它排队/运行中的作业（防重叠）。

补跑作业：`kind="RETRY"`、沿用冻结的 owner/credential/generation、门店=本轮失败集合、
`retry_round = 原+1`、`not_before = max(now + job_retry_delay_seconds(60), cooldown_until)`；
`lease_next_job` 不会提前领走它。用新作业而不是重排原作业：检查记录里可以分别看到两轮，
且推送按 (job_id, channel) 去重，不会吞掉失败轮的通知。

手动「仅重试失败门店」（`POST /scans/{id}/retry-failed`）保留，语义不变。

## 推送覆盖（哪类变化一定会发）

检查结束时的入队（`push.enqueue_for_job`）按用户可见的四类变化收敛，**任何一类被静默丢弃
都视为缺陷**：

| 变化 | 事件 | 开关 |
| --- | --- | --- |
| 补货 | `RESTOCK` | `notify_on_restock` |
| 门店首次有货 / 新上架 | `NEW_ARRIVAL_AT_STORE` | `notify_on_restock`（与补货同类）|
| 售罄 | `SOLD_OUT` | `notify_on_sold_out` |
| 变价 | `PRICE_CHANGE` | `notify_on_price_change` |

- **无任务作业**（手动「立即检查」、任务删除后遗留的补跑）没有任务开关可依，
  按四类全发（标题统一为「门店检查」），不再静默丢消息。
- 价格只在**在货尺码**上抓取，所以「一直没在货」的门店价格会缺失（`price_status=MISSING`），
  这是上游事实而不是推送故障；一旦在货并取到价格，变价即按上表推送。
- 每用户每日推送上限（`push_max_per_day`，默认 200）到顶时不再静默丢弃：
  `GET /me/push-usage` 与前端「消息推送」卡片显示「今日已推送 N/上限」，并提示次日继续。

### 消息里带什么（字段契约）

标题：`【库存提醒】<任务名>`（无任务作业用「门店检查」）；正文按类别聚合，类别行就是变化类型
（补货 / 新上架 / 售罄 / 变价），明细行**固定包含**：

```
· <货号> <尺码> <门店编码>·<门店名> <当前状态> <价格>
```

- 当前状态取变化**之后**的可用性：`有货` / `无货` / `未上架`（`push.AVAILABILITY_TEXT`，
  与钉钉机器人的用词共用同一份映射）。
- 价格：补货/新上架显示到手价或「待补价」；变价显示 `¥旧 → ¥新`。
- 门店名截断到 32 字（生产目录实测最长 31 字，截断只为挡住病态长名），无名时只显示编码，与前端门店选择器
  （`编码 · 名称`）保持一致。
- 例：`· DN3707-202 42 3402·NIKE北京朝阳园 有货 ¥699.00`

### 新店算不算「在监控范围内」

- 「全部门店」任务的名单**在派发时解析**（`scheduler.dispatch_due_tasks`），
  所以之后同步进来的门店从下一轮起自动纳入；前端文案已如实说明
  （`copy.ts::storeHint`）。
- 「指定门店」任务只跑选中的门店，新店不会被动加入（同上文案）。
- 门店目录来自用户自己的 Nike 连接同步（`services.stores.sync_stores`，新店直接 `is_active`）。

### ⚠️ 清理绝不能共用作业事务（2026-10-12 生产事故）

第一版把清理放在作业收尾（`jobs._finalize`）里，且切片超时后 `session.rollback()`——
这一下把**同一个事务里的作业状态、门店结果、变化事件、待投递推送全部回滚**：

* 作业 3 秒内"结束"但状态停在 `RUNNING`（worker 提交时已无内容可提交）；
* 卡住的 RUNNING 作业又让调度器的"同一任务不叠加作业"规则永久挡住新作业；
* 结果：**扫描停摆 ~24 小时 → 没有变化事件 → 钉钉一条推送都没有**（同期钉钉通道本身
  正常、`last_ok_at` 有刷新，Nike 凭证也一直在正常续期——排查时先看这两处会误判为"登录掉了"）。

修复后的约束（**不要回退**）：

1. 清理只在 **worker 空闲循环**里跑，且**另开一个会话**（`prune_idle_slice` →
   `SessionLocal()`），带 `lock_timeout=500ms` / `statement_timeout=3000ms`，失败只跳过这一片；
2. `prune_observation_slice` **不再自己 commit**——事务边界由调用方决定（CLI 逐片提交）；
3. 幂等收尾：即使清理异常，作业事务照常提交（回归测试
   `test_retention_slice_never_touches_a_job_transaction`）。

## 观测历史保留（数据量控制）

监控间隔小（30 秒~10 分钟）× 多门店多货号时，`observation` 一天能涨几百万行——
2026-10-10 生产实测 **752 万行 / 2.4 GB**（当天从 190 万涨上来），而历史只用于回溯。

**策略**：每个 (owner, 门店, 货号, 尺码) 只保留最近 ``NIKE_MP_OBSERVATION_HISTORY_LIMIT``（默认 30）条。

* **稳态**：作业收尾时跑**一小片**（默认 200 个 key）——清理按 key 滚动推进，游标在进程内。
  分片之所以便宜，是因为索引 ``ix_observation_owner_key_checked``
  ``(owner_user_id, store_id, style_id, size_label, checked_at DESC)`` 让"单 key 第 N 条之后"
  变成索引顺序扫描；全局窗口删除（整表排序）在生产 750 万行上每片要几十秒，不可用于稳态。
* **key 来源**：分片从 ``observation_latest`` 取 key（7 万行，代价恒定）——**不变量**：每个写入
  过观测的 key 必有 ``observation_latest`` 行（平台始终 upsert 它），所以不会漏 key。
* **一次性大清理**：``python -m app.cli prune-observations --keep 30 --batch 2000``
  （分片推进直到扫完一轮）；历史上已经堆积到百万级时，用单语句批量删更快：
  ```sql
  DELETE FROM observation WHERE id NOT IN (
      SELECT id FROM (SELECT id, row_number() OVER (
          PARTITION BY owner_user_id, store_id, style_id, size_label
          ORDER BY checked_at DESC, id DESC) rn FROM observation) x WHERE rn <= 30);
  ```
* ``observation_latest``（当前状态）与 ``change_event``（变化流水）**不受影响**，
  界面/矩阵/推送读的都是它们。

## 检测→通知的延迟账（客户拿竞品比"慢 1 分钟"时看这里）

新货在 T 时刻上架，我们通知到人的时刻 = T + 六段之和：

| 段 | 典型 | 上界 | 能不能省 |
| --- | --- | --- | --- |
| ① 等下一轮（`cadence_seconds`） | 0–600s，平均 **300s** | 600s | 客户可调（额度换速度，见容量账）|
| ② 调度 tick（`SCHEDULER_INTERVAL_SECONDS`） | 5s | **10s** | 默认已从 30s 收到 10s |
| ③ 派发抖动（`DISPATCH_JITTER_SECONDS` ≤ 间隔 10%） | 5s | **10s**（10 分钟档）| 默认已从 30s/20% 收到 10s/10% |
| ④ 轮内位置 + 轮次收尾（本轮 28–64s） | ~30s | 64s | 提高并发 / 早推可再省 |
| ⑤ worker 领取作业（`WORKER_POLL_SECONDS`） | ~1.5s | 3s | — |
| ⑥ 投递（`PUSH_DRAIN`，实测 created_at−finished_at） | **0.02s** | ≤3s | 已足够快 |

计费口径修正（405 不计费）后，同样的闸值能跑约 2.4 倍事务量——**这才是把"等下一轮"从
600s 压到 60–120s 的前提**；否则 11 个全店任务 × 60s 会把小时闸打满并触发冷却。
建议口径：**核心货号（1–2 个）用 60–120s，其余维持 600s**，把额度花在"最想抢的那双"上。

## 默认只盯「换季优惠店」（客户要求）

判据（`app/services/stores.py::CLEARANCE_MARKER`）：门店名**含「换季优惠」**。上游 `concept`
区分不出来——2026-10-09 生产库 160 家里 **147 家**是换季优惠店，它们的 `concept` 与普通店同为
`NVS`（另外 13 家是体验店/员工店/Jordan WOF/SKIMS 等）。判据只写在一处，将来上游改名或加字段
只改那里。

默认行为（两条链路都过滤）：

- **获取门店**：`GET /api/v1/stores` 默认 `scope=clearance`（只换季优惠店）；`?scope=all` 看全部。
  数据库仍保留全部门店（改名/判据变化时不用重新同步），只是默认不返回、不监控。
- **监控**：任务的「全部门店」在派发时按同一判据解析（`scheduler.dispatch_due_tasks`），
  所以只跑换季优惠店；指定门店的任务不受影响（用户显式选的照跑）——前端选择器默认只列
  换季优惠店，并有「只看换季优惠店」开关可切到全部。

## 多任务客户的容量账（"任务一多就限速"怎么破）

单店一轮 ≈ 3–5 次计费事务（1 次可用性 PUT + 1–2 次轮询 + 在货尺码的价格批次），
**一轮 160 店 ≈ 500–800 次**；而 `NIKE_MP_QUOTA_HOURLY_CAP` 是**平台级**（所有租户共享）：

| 小时闸 | 160 店任务的可用轮数/小时 | 备注 |
| --- | --- | --- |
| 30000（当前生产） | ≈ 40–60 轮 | 计费口径修正后的等效容量；修正前只有一半 |

已落地的四个杠杆（**都不需要代理**）：

1. **计费口径**：405 挑战与传输失败不记账（见「额度算术」）——同样的闸值买到约 2 倍事务量，
   这正是"任务一多就限速"的主因；
2. **派发抖动**（`NIKE_MP_DISPATCH_JITTER_SECONDS`，实际 ≤ 间隔 20%）：多个任务不再同秒齐发，
   小时额度被摊平，避免"齐发 → 瞬间打满 → 集体冷却"的连锁；
3. **账号级冷却 + 到点补跑**：真撞限速时整轮提前结束、冷却结束先补跑失败门店（见上两节）；
4. **只在货抓价 + 7 天结构缓存**：每个逻辑请求都花在真实变化上。

下一步（未实现，重叠度高时才值得做）：**跨任务探测复用**——同一 owner 下若 (门店, 货号)
在窗口内已被别的作业探过，本轮不再重复探，收益与任务重叠度成正比。风险：第二个任务拿不到
"它自己那条推送"（同一 owner 的渠道已在第一个任务的消息里收到过同一变化），且要按任务开关
分别通知就需要 job↔task 关联；先量化重叠度再决定。

**代理不是这个问题的解**（实测见「已证伪的"绕行"路径」第 9 条）：405 抽签与出口 IP 无关
（12 个全新出口 6/12 通过，χ²≈6.4、p≈0.85），生产 7 天内 403/429 为 0 次。代理只影响
"单出口连接池并发上限"，与额度、拦截率都无关。

## 一轮耗时的构成（与提速旋钮）

单店耗时 ≈ (1 + 价格批次数) × 单次 review 耗时 + 尺码表请求（7 天缓存）。
单次 review = PUT（可能被 405 挑战重试 1–3 次）+ 轮询等待 + 网络往返；价格按
在货尺码 3 个/批，所以「一轮 160 店」的实际时长主要由这两处**固定等待**决定。

| 旋钮 | 默认 | 旧行为 | 说明 |
|---|---|---|---|
| `NIKE_MP_REVIEW_POLL_FIRST_SECONDS` | `0.5` | 固定 2.5s/次轮询 | 首次轮询等待；未就绪才按倍数拉长 |
| `NIKE_MP_REVIEW_POLL_INTERVAL_SECONDS` | `2.5` | 2.5 | 后续轮询的间隔上限（从 first 起翻倍封顶） |
| `NIKE_MP_REQUEST_RETRY_BASE_SECONDS` | `1.5` | 3.5（405）/2.5（5xx） | 上游重试退避基数 `base * 2^(n-1)` |
| `NIKE_MP_REQUEST_RETRY_MAX_SECONDS` | `8.0` | 无上限（3.5→5→6.5→8→9.5→11…） | 退避上限 |
| `NIKE_MP_STORE_CONCURRENCY` | `1` | 1 | 单作业内的门店并发数（1=顺序；建议 3–4，硬上限 8） |
| `NIKE_MP_WAF_STORM_STORE_LIMIT` | `0`（compose 里默认 3） | — | 一轮里这么多家门店被 405 挑战打满重试就熔断（整轮结束 + 冷却 + 补跑）；0=关闭 |
| `NIKE_MP_WAF_RETRY_LIMIT` | `12` | 7（与 5xx/403 共用） | 405 挑战的独立重试预算；只影响被拦的请求 |
| `NIKE_MP_WAF_RETRY_DELAY_SECONDS` | `0.2` | 退避 1.5→3→6→8 | 405 挑战的重试间隔：实测"立即重试"与退避**成功率相同**（7/8 vs 7/8），但每次成功墙钟 **0.43s vs 1.00s**，退避只加时延 |

**WAF 拦截率的实测结论（阿里云 WAF 阻断页，非可解挑战）**：同一时刻做对照，
出口 IP（免费代理 ≈ 生产 IP；香港机房 vs GCP 台北机房同表现）、TLS/JA3 指纹（curl_cffi ≈ httpx）、
HTTP/1.1 与 HTTP/2、UA（Chrome vs 微信小程序）、`x-nike-ux-id`（24 次/臂交错三臂同为 62%）、
`acw_sc__v2` 票据、官网预热 cookie（`acw_tc`/`cdn_sec_tc`）、请求间隔（连发 vs 6s）、
连接复用（keep-alive 75% vs 每次新建 58%，噪声内）、路径/方法变形（大写、编码斜杠、
双斜杠、POST/PATCH）、JWT 有效性（假 token 同样被挡，拦截发生在鉴权层之前）
**都不改变拦截率（≈37–67%）**；拦截率按路径不同：`regions` 100% 被拦、`cart_reviews` ≈50–64%、
`carts` ≈67%，而 `store/home`、`api-test product_details` 为 0%。因此**实时性不能靠降拦截率**，
只能靠：① 门店并发（被拦尝试互相重叠，墙钟不再线性累加）；② 减少每店请求数
（轮询提速、价格跳过已拿到的、结构 7 天缓存）；③ 独立重试预算兜住"连续被拦"的尾概率。

**速率阶梯（静默 2 分钟后，单连接顺序发）**：1/s → 50%、3/s → 56%、10/s → 67%；
平台真实一轮（并发 4、≈13/s）实测挑战率 **64%（576/898 次请求）**，但同一轮的
**逐店 p50 1.82s / p95 3.49s / max 5.27s，161 店中 159 家完成**，整轮墙钟 ≈2 分钟。
即：速率只值 ~15pp 的边际差异，**降速换不回"零挑战"**，却会把整轮拖长数倍——
因此"按拦截率自适应节流"的控制器在设计并测试后**未采用**（收益在噪声内、代价是实时性）。

**2026-10-09 大陆出口实测（决定性问题：大陆 IP 会不会降低拦截率）**

用户提示"先看能不能上百度"，据此又揪出**第三个方法坑**：探活目标必须**大陆可达**——
用 `cp.cloudflare.com` 探活会把真大陆出口系统性滤掉（大陆代理到不了 cf）。改成
`baidu.com/robots.txt` + 特征串（`Baiduspider`）校验后，配合"回显 IP + 直连查询归属"，
才拿到可信样本。

> 结论：**大陆机房出口不但不更好，反而更差**。
> - 8 轮共取 **435 个 CN 候选**（`proxy.scdn.io` 的 `country_code=CN`，身份直连核实为
>   `CN AS37963 阿里云`），仅 **2 个**能隧道 HTTPS 到 Nike（`store/home` 200）：
>   `47.101.159.19:8899` 与 `47.111.175.196:7897`。

>   而同期香港 VPS 直连是 **~60%**。
> - 也就是说：免费池里的"大陆出口"是**最便宜的机房 IP**（阿里云 AS37963，最易被风控标记），
>   换上去只会更糟；免费池既提不高通过率，也不能回答"大陆**住宅/移动**"这个细分假设。

**405 挑战风暴熔断**：线上实测（160 店/轮）worker 日志里 405 占全部上游尝试的 **57%**，
一轮 7–11 家门店因 `WAF_CHALLENGE` 变成 UNKNOWN，整轮要 42–58 分钟。熔断阈值
（默认 3 家 ≈ 需求 D-NFR-RATE-06 的 15% 在 160 店规模上的折算）到达时：整轮立即结束、
账号按风控阶梯进入冷却，剩余门店自动排补跑——把"一小时耗在墙上"换成"退避 5 分钟再来"。

`NIKE_MP_STORE_CONCURRENCY > 1` 时：每个门店在自己的线程 / 数据库会话 / 上游客户端里跑，
检查点仍是逐店独立提交（崩溃/丢租约只影响在跑的那几家）；某个门店命中额度或风控墙时会
立刻停止提交新门店，等在跑的门店收尾后用一次统一中止结束整轮（已成功的门店保持成功，
未完成的统一标 FAILED 并交给补跑）。代价是瞬时上游请求数与配额消耗速度成倍上升——
这正是账号级冷却要兜底的地方。

价格阶段只在「还缺价」的在货尺码上再发请求：小批量的可用性响应本身就可能带回
价格，此时不再重复一次 PUT + 轮询。

**离线实测（stub，仅等待成分）**：`2.51s → 0.51s` / 次 review；按 160 店 × 2 次
推算，一轮从 ≈13.4 分钟降到 ≈2.7 分钟。

**门店级并发实测（stub，40 店 × 1 货号）**：

| 并发 | 整轮耗时 | 单店中位 | 配额消耗 |
|---|---|---|---|
| `c=1` | 43.72s | 1.06s | +160（4.0 次/店） |
| `c=8` | 7.34s（**6.0×**） | 1.16s | +160（同上） |

**额度曲线（关键结论）**：并发只压缩墙钟时间，**不改变配额成本**。
stub 模型下每店 4 次事务（可用性 PUT+GET、价格 PUT+GET），160 店一轮 ≈ **640 次**；
线上还要叠加 405 挑战重试（每次重试也扣 1 次，日志里每店常见 2–3 次），
实际约 **6–10 次/店 → 960–1600 次/轮**，超过 `quota_hourly_cap=900/小时`：

- 因此 160 店任务在一小时内做不完全量：到闸即整轮提前结束（实测 `c=8` + 闸 60：
  恰好停在 60 次、零超发，16 店成功 / 24 店 FAILED），账号进入 `platform_hourly_budget`
  冷却（下一个整点 +30s），并**自动为剩余门店排队补跑**——即"滚动覆盖"，不再是从头再撞。
- 想做到每小时全量覆盖，只能上调 `quota_hourly_cap`（需单独评估上游风控），
  或把任务拆小（按门店分组、不同任务错峰），或接受滚动覆盖。

**线上日志推演（405 挑战样本）**：单次 review 的重试等待 8.5s → 4.5s（2 次重试）、
15.6s → 10.5s（3 次重试）；若风控更严把 `BASE` 调回 `3.5` 即恢复旧节奏。

验证方式：worker 日志里同一 `cart_reviews` 请求 ID 的相邻时间差，以及
`scan_job_store.started_at/finished_at` 的单店时长分布。

## 已证伪的"绕行"路径（别再重复试）

1. **`api-test.nike.com.cn` 不能承载生产数据**：它是**独立认证域**——用刚重授权的新 token
   实测，`regions` / `cart_reviews` / `carts` 一律 **401 空载荷**（同一 token 在生产域
   `regions` = 200）。此前"测试域不触发 WAF（假 token 得 401=已到业务层）"是把**认证层的
   401 误读成了放行**；请求根本没走到 WAF，自然"不被拦"。
2. **`product_details` 的库存/价格字段在测试域是惰性的**：载荷确实带 `product.available`、
   `prices`、`promotions`、`sizes[].status`，但在 **9 组门店×货号**（含遗留文档记录过
   "6 码在售"的 3752/CD7069-003）上实测：`available` 恒 `false`、价格恒 0、`status` 恒
   `INACTIVE`。只可信 `sizes[].localizedLabel` / `gtins`（尺码表）。
3. **多 IP / 代理轮换**：一边撞上同一拦截率，一边把账号打成 `NEEDS_AUTHORIZATION`
   （账号在多 IP 间抖动会被风控判为异常），已禁用。
4. **长静默让标记衰减**：在平台停扫后仅静默 2 分钟即测，1/s 仍有 50% 挑战；
   更长静默（≥25 分钟）因不能停服而未测完，不作为设计依据。
5. **跨域复用 `acw_sc__v2` 票据**：在 `accounts.nike.com.cn` 的 authorize 页确实拿到了票据
   （cookie：`acw_sc__v2` / `acw_tc` / `emperor_id`，页面 282 KB，无需解题即下发），但把该
   cookie 带到 `api` 域后 A/B 无差异：基线 405 **12/20**、带 cookie jar **13/20**、
   显式 `Cookie` 头 **10/20**（n=20/臂，全部单请求）——WAF 票据**不跨域生效**。
6. **换出口 IP（免费代理实测，已授权）**：两轮共抓 3000+ 个免费代理，明文探活后仅约 30 个可用；
   对 12 个存活出口各发 **20 次**单请求，405 率 **30%–55%**，与本机直连（40%–60%）统计上一致；
   同一批里既有 3/3 全拦也有 2/3 通过的出口——**拦截率与出口 IP 无关**（可达范围内的机房 IP
   同一分布）。
7. **`mp.nike.com.cn`（杭州阿里云，Spring Boot）看似免 WAF，实则应用层全局鉴权拦死、不可用**：它对 `/o2o/*`、
   `/store/*` 一律 HTTP 200 且从不 405（30/30 假 token 通过），凭据走 **`token` 请求头**
   （JWT 形态 → `{"msg":"token失效，请重新登录","code":401}`；非 JWT → `{"msg":"invalid token"}`）；
   **刚刷新过的生产 token 也被判失效**；`/oauth/token`（form 编码）对所有 grant 返回
   `{"msg":"未知异常，请联系管理员","code":500}`。它需要自家签发的会话 token，签发要在微信
   客户端上下文里完成——超出"禁止客户端控制"的边界。
   **补充复核（同日）**：mp 域**并非"无 WAF"**——`/actuator/env` 会命中同一个阿里云 WAF 405 页；
   其余路径（含 `/actuator/*`、`/swagger-ui*`、`/v2|v3/api-docs`、`/openapi.json`，响应均 34 B）
   一律被其**应用层全局鉴权过滤器**拦下，actuator/文档端点并未暴露。
   `accounts.nike.com.cn` / `m.nike.com.cn` 同样不出现 405，但也不路由 `/o2o/*`、`/store/*`
   （404 JSON 信封）。域名穷举：`svs/unite/cart/buy/api2/api-uat/h5.nike.com.cn` 均无解析、
   `app.nike.com.cn` 无响应——**没有任何其它域路由 `/o2o/*`，`api.nike.com.cn` 是唯一入口**。
8. **结论**：`api.nike.com.cn` 的 `/o2o/*` 405 就是阿里云 WAF 的 **CC 防护拦截页**
   （官方文档原文："您可以设置 CC 防护规则，拦截针对网站页面请求的 CC 攻击，并返回 405
   拦截提示页面"）。它按速率/统计判定，**与请求头、请求体、出口 IP、票据都无关**，也没有
   可解的"挑战"；"请求体"一类技巧在逻辑上也不成立——**无 body 的 GET（`carts`）与带 body
   的 PUT 拦截率相同**。能改变拦截率的只有请求量/速率（本次需求已排除）或服务端策略调整。

9. **多 IP + 多特征"池化轮换"**（用户假设：不必一个出口全通，多个出口轮着把访问做完）：实测否掉——
   ① 对 12 个**从未用过**的出口各发**首次**请求：通过 **6/12 = 50%**（与重度使用的本机 IP 同分布）；
   ② 稀疏轮换（3 轮 × 12 出口，每出口相邻 ≥24 s，同时轮换 5 种 UA/特征）：通过 **20/36 = 56%**。
   把 12 个出口各 20 次的累计通过率做同质性检验：**χ²≈6.4（df=11，p≈0.85）**——各出口 p 统计同质
   （≈0.41–0.50），**不存在可利用的"好出口/好特征"**。因为每次请求是独立同分布的硬币
   （p≈0.5），池化并不改变"每逻辑请求的期望尝试次数 = 2"这一事实；现有 0.2 s 近即时重试
   已接近理论最优（每逻辑请求 ≈0.35–0.7 s，理论下限 ≈2 次网络往返）。

**仍未验证的唯一变量**：单一**稳定**的中国大陆住宅/移动出口（手机热点可一次性验证）。
但第 6 条已表明拦截率与出口 IP 无关（12 个不同 ASN 的代理同一分布），即便验证，预期仍是 ~50%——
真正能改变结果的是服务端策略变化，而不是客户端手段。

## 容量：万级/小时怎么达成（2026-10-06 实测）

**拦截率不随速率升级**——决定性发现（单出口、假 token、60 s 窗口、单请求不重试）：

| 门店并发 | 尝试/秒 | **通过/秒** | 405 占比 | p50 延迟 | 折算通过量/小时 |
|---|---|---|---|---|---|
| 4 | 23.1 | 8.4 | 63% | 0.17 s | ≈30,000 |
| 8 | 32.4 | 12.6 | 58% | 0.15 s | ≈45,000 |
| 16 | 93.8 | **33.2** | 57% | 0.17 s | ≈120,000 |

（此前"爆发会退化成近 100% 拦截"来自过滤日志的误读；真实曲线是平的：**WAF 不是吞吐瓶颈**，
它只是"每请求约 40% 通过"的独立硬币，拉到 94 次/秒也不恶化。）

真正的瓶颈是平台侧三道闸，默认值把它们锁死在 ~450 通过/小时：

1. `NIKE_MP_QUOTA_HOURLY_CAP`（默认 `900`，**按到达业务层的应答计次**：405 挑战与传输失败不记账，
   见「额度算术」；实测 ~50% 挑战率下同样的额度买到约 2 倍事务量）；
2. `NIKE_MP_DAILY_REVIEW_BUDGET`（默认 `60000`/天）与**租户** `daily_review_budget`（默认 `5000`/天）；
3. `NIKE_MP_STORE_CONCURRENCY`（默认 `1`；代码上限 `MAX_STORE_CONCURRENCY`，已按实测上调到 32）。

**通过量 1 万/小时的最小配置**（按 ~60% 拦截率反推 ≈2.5 万次尝试/小时）：

```bash
# /opt/nk-mp/.env
NIKE_MP_QUOTA_HOURLY_CAP=30000
NIKE_MP_QUOTA_HOURLY_SLOW_LINE=24000
NIKE_MP_DAILY_REVIEW_BUDGET=1000000
NIKE_MP_STORE_CONCURRENCY=16
# 租户日预算（库内）
update tenant set daily_review_budget = 1000000;
```

**需求面**：平台只跑任务要求的量——一轮 160 店 × 1 货号 ≈ 400 个逻辑请求（≈800 次尝试）。
要持续 1 万**通过**/小时，需要 ≈25 轮/小时（节拍 ≈2.4 分钟）**或**把监控面放大到多货号
（每加一个货号，一轮逻辑量近似翻倍）。节拍与货号数是产品侧开关，平台侧已就绪。

**风险**：放开的是自家闸门，上游仍是那枚 ~40% 的硬币；把尝试量推到十万/小时级别属于对
Nike 边缘的持续压测，可能触发更强风控（今天是"按请求抽样"级别，尚能自愈）。建议先按
通过量 1–2 万/小时运行，盯 405 占比与门店成功率，再逐步上调。

## 出口池与指纹轮换（一请求一出口、一请求一特征）

```bash
# /opt/nk-mp/.env
NIKE_MP_PROXY_URLS_FILE=/data/proxies.txt   # 容器内路径（宿主 ./runtime 挂载到 /data）
NIKE_MP_PROXY_COOLDOWN_SECONDS=120          # 传输层失败后该出口冷却秒数（405 是常态，不算失败）
NIKE_MP_FINGERPRINT_ROTATION=true           # 每请求轮换 UA / 客户端提示
```

- **列表文件**：每行一个 `http://ip:port`，`#` 注释；worker 每 60 s 检查 mtime 自动重载，
  **换池不必重启容器**。宿主侧 `./runtime` 挂载进 worker（`/data`，只读）与 api（`/data`）。
- **轮转语义**：每个上游尝试取下一个健康出口（一请求一出口）；出口只在传输层失败时冷却，
  405 只说明这次抽到了"拦"，不影响出口健康、也不打断轮转。
- **粘性模式**：`NIKE_MP_PROXY_STICKY=true` 时不再"一请求一出口"，而是钉住同一条出口
  （列表里放一条即整账号走那一条）；坏出口冷却期间临时让位、冷却结束自动回到钉住的那条。
  何时用：拿到**大陆住宅/移动**这类"稳定出口"时；**不要**对住宅池开轮换——实测多 IP 抖动
  会把账号打成 `NEEDS_AUTHORIZATION`。
- **抓取器**：`qa/fetch_proxies.py`（22 个免费源 → 明文探活 → 经代理 CONNECT 打 Nike 非 WAF 路径验证，
  只保留真能隧道 TLS 到 `api.nike.com.cn` 的出口）。实测一轮：解析 54,426 条候选 → 抽检 6,000 →
  明文存活 595 → **可用出口 114**。
- **定时刷新**：随栈自启的 `proxy-refresh` 边车（`qa/` 只读挂载 + `runtime` 共享），每 15 分钟重跑
  抓取器并**原子替换**列表（空结果不覆盖旧池），日志落在宿主 `runtime/fetch.log`——不依赖宿主 cron。
  手动刷新：`docker compose exec -T api python - < qa/fetch_proxies.py > runtime/proxies.txt.tmp && mv runtime/proxies.txt.tmp runtime/proxies.txt`。
- **收益与代价**：免费代理普遍慢且抖动（p50 明显高于直连的 0.17 s），池化的价值是
  **并发上限与出口独立性**（避免单 IP 连接打满、避免单点被限），而不是提高单请求通过率——
  实测单请求通过率与出口 IP、特征无关，稳定 ≈40%。

单元测试：`apps/api/tests/test_egress.py`（9 例：轮转、冷却/恢复、全冷却回退、换池、列表解析、
指纹轮换开/关、每请求不同出口、失败冷却并换出口重试）。

### 实测：免费池能"一请求一出口"，但撑不起吞吐

用真实 `NikeClient`（16 线程 × 60 s）走 114 个免费出口：

| 指标 | 结果 |
|---|---|
| 尝试 | 30 次（0.1/s） |
| **通过** | **0（0.0/s ⇒ 折算 0/小时）** |
| 异常 | 30（27×`ScanError`＝12 次 405 重试耗尽；3×`NikeTransportError`） |
| 出口使用 | 114 个中用到 **103 个**，**一请求一出口成立** |
| 延迟 | p50 **37.24 s**、p95 138.90 s |

免费代理又慢又死：单请求被拖到几十秒，重试预算全被耗光。因此**生产出口保持直连**——
实测直连 16 并发即 ≈33 次/秒通过（≈12 万/小时），是当前唯一可用的吞吐来源；池化只在
拿到**稳定池**（付费/自建）时才打开：

```bash
printf '\nNIKE_MP_PROXY_URLS_FILE=/data/proxies.txt\n' >> /opt/nk-mp/.env
cd /opt/nk-mp && docker compose up -d worker
```

免费池仍由 `proxy-refresh` 边车每 15 分钟刷新一次（`runtime/proxies.txt`），随时可用于
实验或低价值流量；关掉它会随之停止刷新（`docker compose stop proxy-refresh`）。

### 实测：付费住宅代理（1024proxy）在网关侧封禁 `*.nike.com.cn`

代理本身可用（同一 sid 打 `ipinfo.io`/`baidu`/`google`/`example.com` 均 200，出口 IP 各不相同），
但**Nike 中国全系域名被服务商拉黑**——明文能读到它自己的拒绝对话，HTTPS 则直接掐断连接
（`UNEXPECTED_EOF_WHILE_READING`）：

```
api.nike.com.cn         HTTP 403  'msg: api.nike.com.cn:80 is ban'
api-test.nike.com.cn    HTTP 403  'msg: api-test.nike.com.cn:80 is ban'
www/accounts/mp/static.nike.com.cn、nike.com.cn   HTTP 403  '… is ban'
example.com             HTTP 200        nike.com（国际）  HTTP 301
```

排查过程（全部在已加白名单的生产机上验证，排除误判）：

| 假设 | 结果 |
|---|---|
| 容器出口 IP 未加白名单 | ✗ 宿主与容器出口同为 `103.231.59.72`，且宿主侧同样被拒 |
| 端点短命（API 模式 1 分钟 TTL） | ✗ 静态网关（auth 模式）与 API 模式表现一致 |
| 凭据/鉴权错误 | ✗ 同一凭据打 `ipinfo.io` 200；网关 `CONNECT` 也建立成功 |
| 并发上限 | ✗ 并发 1 也一样（`ConnectError`，p50 0.47s） |
| **目标域名被封禁** | ✓ 明文 403 文案 + HTTPS 掐断，仅 `*.nike.com.cn` 命中 |

结论：这是服务商的域名黑名单，**与 sid/白名单/并发/协议无关**（但**可按字符串绕过**，见下一节
的两种实测方式）；要用住宅池需绕过它或让服务商在面板/工单里解禁。因此生产继续走直连出口
（16 并发实测 ≈33 次/秒通过 ≈12 万次/小时，已满足万级/小时），池化能力保留为可选开关
（`NIKE_MP_PROXY_URLS_FILE`；刷新器 `qa/fetch_paid_proxies.py` 与 `proxy-refresh` 边车默认停用）。

### 补充（同日第二轮 sid）：封禁可绕过，但付费池实测仍不可用

服务商的域名黑名单是**按字符串**判断的，两种方式能绕开（均在已加白名单的生产机实测）：

| 方式 | `store/home`（非 WAF 路径） | o2o 路径 |
|---|---|---|
| 域名直连 | `403 'msg: … is ban'`（服务商） | `000`（连接被掐） |
| 大写域名 `API.NIKE.COM.CN` | **200** | **403**（Nike 边缘对异常 Host 的拒绝页） |
| `--connect-to` 走 IP（CONNECT 目标是 IP，SNI/Host 不变） | **200** | **405**（正常 WAF 拦截页） |

绕过封禁后，用 30 条 sid 打 o2o（单请求、不重试）的结果：

```
明细: {'405': 15, '403': 11, '000': 4}      # 0 个到达业务层（401/400）
延迟 p50 3.54s  p95 11.49s
```

即 **0/30 到达业务层**：50% 被 WAF 拦（与直连同量级）、37% 被 Nike 边缘再拒（住宅代理段被额外
限流）、13% 超时；延迟比直连高一个数量级（3.5s vs 0.15s）。**付费住宅池在通过率与时延上全面
劣于直连**，不接入生产（与"拦截率与出口 IP 无关"的既有实测一致）；池化能力仍保留为可选开关。

## 边界

- 不上调平台闸与租户日预算；要更快需单独评估上游风控与成本。
- 405 挑战按"近即时重试 + 独立预算"处理，不触发账号冷却；风暴熔断
  （`NIKE_MP_WAF_STORM_STORE_LIMIT`，compose 默认 3）在挑战打满许多门店时结束整轮并补跑。
- 30 秒档下通知仍按「一轮一条汇总」发送，不改事件聚合与每用户每日推送上限。
- 补跑作业与下一轮全量可能对少数门店重复覆盖：以「不饿死尾部门店」优先。
