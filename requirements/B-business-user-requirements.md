## 0. 前提与不可动摇的约束（继承 00-project-context）

| 编号 | 约束 | 业务含义（本文件如何体现） |
|---|---|---|
| C1 | 只用纯 API（无 adb/模拟器/OCR/截图/Frida） | 所有客户可见功能只能基于 6 类接口口径；不承诺"店里有什么货"的全量清单 |

## 1. 业务目标与成功指标

### 1.1 业务定位与客户细分

- 业务形态：**订阅制门店监控服务**（卖"折扣信息 + 货源线索"），不是卖软件、不是卖数据文件。
- 对标：NVS 监听平台（私有部署、后台配置"货号 + 尺码 + 门店"、钉钉 Webhook 推送、`maxWatchItems` 配额）。
- 客户画像（按使用动机分 4 类，决定配额与通知偏好）：

| 客户类型 | 核心诉求 | 典型动作 | 对延迟的容忍 | 首选通道 |
|---|---|---|---|---|
| 折扣店/尾货店主 | 低价补货、跨店调货 | 盯 20-50 个货号 × 全国/本省店 | 小时级可接受 | 钉钉群 + 每日汇总 |
| 买手（批量扫货） | 某货号"哪家店还有我的码" | 全国扫描 + 导出清单 | 越快越好（小时级） | 钉钉 + 短信（高价值） |
| 代购 | 断码恢复、热门码补货 | 盯少量货号 × 少量门店 | 越快越好 | 钉钉/企微 |
| 零售商从业者（选品） | 上新、大促节奏、折扣规律 | 上新墙 + 活动专区 + 历史 | 天级可接受 | 邮件日报/周报 |

### 1.2 服务方视角指标（可量化，可作为后台首页 KPI）

| 指标 | 定义 | 目标（首年） | 优先级 |
|---|---|---|---|
| 付费客户数 | 活跃订阅客户 | 10 → 20 | P0 |
| 客户月活跃率 | 当月有登录或收到有效提醒 | ≥ 90% | P0 |
| 月续费率 | 次月仍付费客户占比 | ≥ 80% | P0 |
| 任务审核成功率 | 单轮任务中成功完成审核的"店·轮"占比（含 WAF 重试与补测） | ≥ 99%（单次尝试 ≥97% 即可接受，靠补测补齐） | P0 |
| 端到端及时性 | 变化发生 → 客户收到通知，P95 | ≤ 刷新周期 + 90 s | P0 |
| 假阳性率 | 推送后又确认为未发生的变化 / 总推送 | **0**（硬指标，见 C4） | P0 |
| 客户判定误报率 | 客户点击"无效提醒"占比 | ≤ 5% | P1 |
| 零维护达成度 | 需人工介入次数 / 月；需客户操作的次数 / 月 | ≤ 1 次/月且 ≤15 min；**客户操作 = 0** | P0 |
| 新客户上线时长 | 后台建户 → 首条提醒 | ≤ 10 min 配置 + 首个扫描周期内出结果 | P0 |
| 容量水位 | 账号池"店·轮"用量 / 安全产能 | ≤ 70% | P0 |
| 账号健康 | 因风控产生 401/冷却的次数 | 0 次/天（容量规划目标） | P0 |
| 单位经济性 | （客户月费 − 采集/账号/短信成本）/ 月费 | 毛利 ≥ 60% | P1 |

### 1.3 客户视角指标（对外可宣传的口径）

| 指标 | 定义 | 目标 | 优先级 |
|---|---|---|---|
| 首条有效提醒到达时间 | 开通 → 首条客户认可有用的提醒 | ≤ 24 h | P0 |
| 补货提醒转化率 | 被客户标记"已抢到/已用上"的补货提醒占比 | ≥ 30% | P1（需 UI 反馈按钮） |
| 提醒可执行率 | 提醒中含"门店 + 尺码 + 价格 + 深链"四要素的比例 | 100% | P0 |
| 漏报投诉 | 客户发现但系统未提醒的次数 | 0/月 | P0 |
| 周活跃 | 每周查看/接收 ≥ 3 天 | ≥ 70% 客户 | P1 |
| 覆盖度承诺 | 客户关注货号在所选门店范围内 **逐店** 核对（不允许抽样） | 100% | P0 |

> 注意：无法度量"客户真实成交"，只能靠"已抢到"手动标记近似；不要对外承诺"销量提升 X%"。

### 2.2 角色说明

- **R1 服务方管理员（Operator Admin）**：唯一持有 Nike 采集凭证与账号池的人；负责租户生命周期、配额、全局调度与风控参数、通道配置、审计。日常不介入具体客户业务。
- **R2 服务方运营/客服（Operator Support）**：面对客户的一线；能看任何客户的运行状况与推送记录，能代跑任务、补扫、重发通知、发布服务公告；不能改凭证与套餐（防误操作），不能看凭证明文。
- **R3 客户主账号（Customer Owner）**：客户侧负责人（店主/老板/买手负责人）。全权管理本客户的货号、门店、通道、成员、配额；是本客户的账单与协议主体。
- **R4 客户子成员（Customer Member）**：店长/店员/买手。在授权范围（门店/货号/事件类型）内建任务、查询、接收通知、导出；不能改通道、成员、套餐。
- **R5 只读访客（Customer Viewer）**：外部合作买手/临时同事。仅能看指定看板或接收汇总消息，不能建/改任何配置；通过带 token 的分享链接访问（有效期可设），不做完整账号体系。

### 2.3 系统角色（非人类，但需在需求中建模）

- **SY1 调度器（Scheduler）**：按"门店 × 时间窗"聚合所有客户的货号，合并为 ≤40 件的可用性批次（价格批次 ≤3 件）。
- **SY2 通知网关（Notifier）**：去重 → 确认 → 静默 → 聚合 → 按 20 条/分钟通道限流下发。
- **SY3 健康哨兵（Sentinel）**：凭证余量、JWT 续期、WAF 挑战率、连续失败轮次、通知失败率；异常时先告警服务方，再决定是否对客户展示"数据延迟"。
- **SY4 配额守卫（Quota Guard）**：按客户限额扣减"店·轮"，超限降频而非直接报错。

## 3. 典型用户场景 / 用户故事（User Stories）

> 格式：`- [ ] **US-xx [P0/P1/P2]** 作为…，我想…，以便… ｜ 验收：…`

### 3.1 服务方管理员 / 运营（R1、R2）

- [ ] **US-O-01 [P0]** 作为服务方管理员，我想在后台**一次性**维护采集账号与凭证（refresh_token 自动轮换、JWT 自动续期），以便 10-20 个客户完全不需要登录、授权或做任何维护。
  ｜验收：客户侧无任何 Nike/微信登录入口；凭证剩余有效期 <25% 时自动告警并自动续期；全程无客户介入。
- [ ] **US-O-02 [P0]** 作为服务方管理员，我想让调度器按**门店 × 时间窗**合并所有客户的货号（可用性 40 件/批、价格 3 件/批），以便 在接口限制下摊薄成本、支撑更多客户。
  ｜验收：同店同窗口多客户货号合并入同一批；单轮全国 100 店扫描 ≤ 45 min；单账号并发上限可配。
- [ ] **US-O-03 [P0]** 作为服务方管理员，我想有一个接口健康面板（成功率/延迟/405 挑战率/401 次数/凭证状态/容量水位），以便 在客户发现问题之前先发现。
  ｜验收：任一指标准超阈值自动告警（站内 + 服务方钉钉）；可下钻到具体门店/货号/时间窗。
- [ ] **US-O-04 [P0]** 作为服务方管理员，我想给客户设置套餐与配额，并实时查看其用量（店·轮/天、推送条数），以便 在超卖或超额前限流与升级销售。
  ｜验收：后台可改任意客户的配额并即时生效；用量曲线保留 ≥90 天；达到 80%/100% 分别告警。
- [ ] **US-O-05 [P0]** 作为服务方运营，我想在数据不可信时（空完成响应、WAF 405、401、TLS 错误）让系统自动重试并在**未确认前抑制通知**，以便 绝不把假的"售罄/补货"推给客户。
  ｜验收：同状态需连续 2 次一致观测才生成事件；重试与补测过程记录可查；假阳性率 = 0。
- [ ] **US-O-06 [P0]** 作为服务方运营，我想当某客户全部任务连续 2 轮失败时先收到告警并让该客户看到"数据延迟"状态，以便 客户来问之前我们已经知道。
  ｜验收：客户侧页面/消息显示"数据截至 HH:mm，因上游异常延迟"；服务方告警 ≤5 min 内到达。
- [ ] **US-O-07 [P1]** 作为服务方管理员，我想配置全局限速与自动冷却（店·次/秒、突发上限、401 后暂停 N 分钟），以便 避免账号风控冷却、保住长跑稳定性。
  ｜验收：压测下 24 h 无 401/冷却；限速变更不需重启服务。
- [ ] **US-O-08 [P1]** 作为服务方管理员，我想在接口变更或账号异常时一键切换备用账号、并把服务公告推给全部客户，以便 快速止损且客户知情。
  ｜验收：切换 ≤2 min 完成；公告一次配置、多渠道下发、客户可见历史公告。
- [ ] **US-O-09 [P1]** 作为服务方运营，我想查看每条通知的下发/到达/失败/客户反馈日志，以便 支撑 SLA 举证与计费。
  ｜验收：可按客户/任务/通道/时间检索；导出 CSV；保留 ≥180 天。
- [ ] **US-O-10 [P1]** 作为服务方运营，我想代客户补扫某货号某门店（客户报"我刚才看到有货但没提醒"），以便 快速排障并给出证据。
  ｜验收：可在后台对任意 (货号, 门店) 触发即时核对，输出含时间戳与原始响应摘要的凭证。
- [ ] **US-O-11 [P2]** 作为服务方管理员，我想用 CSV 批量导入新客户及其初始货号清单，以便 5-10 分钟上线一个客户。
  ｜验收：导入后自动完成首轮全量扫描并发出欢迎+首份报告。

### 3.2 客户主账号（R3）

- [ ] **US-C-01 [P0]** 作为客户主账号，我想输入货号（如 `DN3707-202`）创建监控任务并勾选门店范围，以便 让系统替我盯这些货，而我不需要做任何技术配置。
  ｜验收：支持货号校验与提示（无效货号给出明确文案）；创建后 ≤1 个刷新周期内开始产生数据；可暂停/恢复/删除任务。
- [ ] **US-C-02 [P0]** 作为客户主账号，我想对某货号做"全国 100 店扫描"并看到**尺码级**有货情况（有货列出尺码，无货标灰），以便 判断哪个城市哪家店能买到我要的码。
  ｜验收：结果按"门店 × 尺码"矩阵呈现；每行含门店名/城市/店号/价格；明确区分"该店不卖此款"与"该店卖但此码缺货"；100 店扫描 ≤45 min 出结果。
- [ ] **US-C-03 [P0]** 作为客户主账号，我想在**补货/断码恢复**时立刻收到推送（货号、品名、门店、尺码明细、价格、时间、深链），以便 马上安排到店或让买手去抢。
  ｜验收：消息四要素齐全（门店+尺码+价格+深链）；同一事件不重复轰炸（见 §5.2）；含"数据可信"标记。
- [ ] **US-C-04 [P0]** 作为客户主账号，我想在**门店价格/促销变化**时收到提醒（标价 → 实付、促销名），以便 抓住低价窗口采购。
  ｜验收：变价消息含原价/实付/折扣名；无法取得价格时（该店该款部分缺货）明确告知"价格暂不可得"而非留空；不对价格做猜测。
- [ ] **US-C-05 [P0]** 作为客户主账号，我想知道某货号在我关注门店是否"售罄→有货"或"全店下架/不可购"，以便 区分"卖完了"和"这家店不卖"。
  ｜验收：状态字典固定为 {有货(列码) / 该码缺货 / 该店不卖 / 审核未完成}；不出现"未知"以外的模糊状态。
- [ ] **US-C-06 [P0]** 作为客户主账号，我想看到本客户套餐用量与配额余量（货号数、门店数、刷新频率、今日推送条数），以便 提前清理无用任务或升级套餐。
  ｜验收：用量实时（≤5 min 延迟）；达到 80% 时提醒；超限时降频而非静默失效（见 §4.4）。
- [ ] **US-C-07 [P1]** 作为客户主账号，我想查看某货号×门店的**历史变化时间线**（补货★/售罄✗/变价¥/上新），以便 复盘节奏、判断何时下手。
  ｜验收：时间线可按货号/门店/事件类型筛选；注明"仅含服务上线后的记录"，绝不伪造历史；可导出。
- [ ] **US-C-08 [P1]** 作为客户主账号，我想在**地图上按城市/大区勾选门店**（或一键"全国/本省"），以便 快速圈定我的门店范围。
  ｜验收：默认展示 100 家门店（含店名/地址/门店类型：换季优惠店/品牌体验店）；支持批量全选/反选/按大区；保存为"我的门店组"供任务复用。
- [ ] **US-C-09 [P1]** 作为客户主账号，我想把扫描结果**导出 Excel/CSV 或生成带有效期的分享链接**发给同事，以便 内部协作与报价。
  ｜验收：导出含货号/门店/尺码/价格/核对时间；分享链接可设有效期与只读；链接可随时失效。
- [ ] **US-C-10 [P1]** 作为客户主账号，我想配置**免打扰时段与每日汇总时间**，以便 夜里不被消息炸、早上一次看全。
  ｜验收：默认 22:00–08:00 静默（P0 级事件可配置为例外）；静默期事件进队列，次日 8:30 汇总为一条。
- [ ] **US-C-11 [P1]** 作为客户主账号，我想管理子成员与其**通知订阅范围**（谁收哪些门店/货号/事件类型），以便 团队分工不互相打扰。

## 4. 套餐 / 配额模型建议

### 4.1 成本驱动因子（必须先讲清，因为它决定配额能开多大）

- 实测口径：**100 店 × 1 货号全量核对 ≈ 35-40 min**（含轮询与重试）→ 单条采集通道 ≈ 150 店·轮/小时。
- 单账号 24 h 不应满载（风控 + 间歇 405 挑战）→ **建议按 30% 左右占空比规划安全产能：单账号 ≈ 1,000–3,000 店·轮/天**（需实测校准）。
- 定义：**1 店·轮 = 对 1 家门店做 1 次批量核对（≤40 货号）**；价格核对（≤3 件/批）只在需要变价提醒时额外消耗。
- 计费权重公式（后台内部计量）：
  `日成本(店·轮) = Σ_任务 [ 门店数 × 每日刷新次数 × ceil(货号数 ÷ 40) ]`
- 关键节约杠杆（必须在架构里落地）：**跨客户按门店聚合批次** —— 同一门店的多个客户货号合并为一批，成本与客户数弱相关；否则 20 个客户线性叠加会直接击穿账号池。
- 规模提示：20 客户若都按"50 货号 × 100 店 × 每小时"（≈4,800 店·轮/天/客户）计，总计 ≈ 9.6 万店·轮/天 → 需 30+ 个采集通道/账号。**结论：频率与门店范围是最贵维度，必须在档位里严格分级**（并把"每天 2-3 次"设为基础档默认）。

### 4.2 配额维度（对客户可见）

| 维度 | 说明 | 是否硬限 | 计量 |
|---|---|---|---|
| 监控货号数 | 同时生效的货号任务数（= NVS `maxWatchItems` 口径） | 硬限 | 个 |
| 门店范围/任务 | 全国 100 店 / 按大区 / 自选门店组 / 单店 | 硬限 | 店数 |
| 刷新频率 | 最低刷新周期（15/30/60/180/360 min，或"每日 N 次"） | 软限（可下载额度） | 次/天 |
| 价格核对 | 是否开启变价监控（显著更贵，3 件/批） | 档位开关 | 开/关 |
| 通知通道数 | 钉钉/企微群机器人、邮件收件人、短信条数 | 硬限 | 个/条 |
| 历史回溯 | 时间线可查天数 | 硬限 | 天 |
| 子账号数 | 主账号 + 子成员 + 访客链接数 | 硬限 | 个 |
| 导出/分享 | 月导出次数、分享链接并发数 | 软限 | 次/月 |

### 4.3 档位建议（表格式）

| 档位 | 监控货号 | 门店范围 | 刷新频率 | 变价监控 | 通知通道 | 历史 | 子账号 | 内部额度（店·轮/天） | 参考月价（待定） |
|---|---|---|---|---|---|---|---|---|---|
| 试用（7 天） | 3 | ≤10 店 | 每 6 h | ❌ | 钉钉 1 群 | 7 天 | 1 | ≤100 | 免费 |
| 基础 | 10 | ≤30 店 | 每 3 h（或每日 4 次） | ❌ | 钉钉 1 群 + 邮件 | 30 天 | 3 | ≤400 | 待拍板 |
| 标准 | 30 | ≤100 店 | 每 1 h | ✅ | 钉钉 2 群 + 企微 1 + 邮件 | 90 天 | 8 | ≤3,000 | 待拍板 |
| 专业 | 80 | 全国 100 店 + 门店组 | 每 30 min（重点货号 15 min） | ✅ | 全部 + 短信 N 条 | 180 天 | 20 | ≤10,000 | 待拍板 |
| 定制/企业 | 200+ | 全国 + 特殊需求 | 15 min（限额内） | ✅ | 专属通道 | 365 天 | 不限 | 面谈（账号池扩容） | 面谈 |

- 计费建议：**按年/半年预收**（降低续费摩擦）+ 超量按"店·轮"包叠加，不按消息条数计费（消息条数与价值不成比例，且会诱发客户少收提醒）。
- 演示承诺口径：报价页必须同时写"**刷新频率即数据新鲜度**"，避免客户误以为是实时库存（见 §6.2 话术）。

### 4.4 配额执行规则

- 超出硬限（货号/门店/通道）：创建时即拒绝，提示"升级套餐"或"删除某任务"。
- 超出软限（额度）：**降频不失效** —— 自动把最低优先级任务拉长周期，并在客户侧显著提示"因额度不足，X 个任务已降频至每 N 小时"。
- 额度分配优先级：客户显式标记"重点"的任务 > 创建时间早的任务 > 其他。
- 用量统计口径与后端限速参数（店·次/秒、并发）必须联动，禁止"配额允许但账号池供不上"的静默失败。

## 5. 通知渠道需求

### 5.1 渠道优先级与接入约束

| 优先级 | 通道 | 接入约束 | 适用消息 | 备注 |
|---|---|---|---|---|
| P0 | **钉钉群机器人（自定义 Webhook）** | 客户自建群 + 机器人，需 webhook + 加签 secret；官方限流约 **20 条/分钟/机器人**；支持 markdown/卡片（可带跳转链接） | 补货/变价/断码恢复即时提醒 | 对标 NVS，首选；服务方需做 50% 余量的令牌桶（≤10 条/min/机器人） |
| P1 | **企业微信群机器人** | 群机器人 webhook；同样约 20 条/分钟；无加签（URL 含 key，需按密钥保管） | 同上（客户不用钉钉时） | 消息格式能力略弱于钉钉（卡片/跳转受限） |
| P1 | **邮件** | SMTP 即可，无认证门槛；可带 Excel 附件 | 日报/周报、失败兜底、账单 | 触达弱但零成本、可归档，作为"兜底通道"必选 |
| P2 | **短信** | 需企业实名 + 签名与模板报备（阿里云/腾讯云），成本约 0.03–0.05 元/条 | 仅高价值事件（如重点货号补货）或"提醒异常"告知 | 建议作为付费增值包（N 条/月），不默认开启 |
| P2 | **微信服务号（订阅通知/模板消息）** | 需企业认证服务号（年费）+ 模板/订阅审核；一次性订阅需用户主动授权，**不适合无人值守**；长期订阅仅限特定行业 | 汇总类消息（若能拿到长期订阅权限） | 与"客户零微信占用"不冲突（只做接收端），但接入与维护成本高 → 建议 P2，用"只读网页 + 邮件/短信"替代 |
| ❌ | 电话/语音、客户个人微信（非官方接口） | 违规或干扰客户 | — | 明确不做 |

### 5.2 去重 / 确认 / 静默 / 聚合策略（P0）

1. **状态确认（防抖动）**：同一 (客户, 门店, 货号) 的状态必须**连续 2 次一致观测**才生成事件；单次观测变化记为"待确认"，不推送。空完成响应、审核失败一律**不参与**状态推进（C4）。
2. **事件唯一键**：`(tenant_id, store_id, style_code, size, event_type)`；同键在静默期内只推一次。
3. **静默期**：默认同一 `(门店, 货号, 事件类型)` **60 min** 内不重复推送；可配 0/30/60/180 min；按客户维度生效，互不影响。
4. **聚合窗口**（默认 60 s，可配）：
   - 一轮扫描内多店同事件 → 按 **货号** 聚合成 1 条（列出各门店 + 尺码）；
   - 一轮内同店多货号 → 按 **门店** 聚合成 1 条（列出货号列表）；
   - 窗口内事件 >10 条 → 自动降级为"摘要 + 详情链接"。
5. **通道限流感知**：网关按通道令牌桶发送，超限进队列并在窗口后合并；通知积压 > N 条时自动转为摘要（避免晚到的一大堆过期消息）。
6. **分级策略**：即时（补货 / 断码恢复 / 大幅变价）→ 准即时（常规变价）→ 汇总（上新、每日盘点、周报）。
7. **免打扰**：默认 22:00–08:00 静默并次日 8:30 汇总；客户可把个别货号设为"全天候"。
8. **不推"无意义变化"**：同一价格的分位抖动（如 ±0）、数据缺失导致的"疑似售罄"、审核失败导致的空状态，一律不推。

### 5.3 消息内容与失败处理

- **必含要素**（P0）：货号 + 品名 + 事件类型 + 门店（店名/城市/店号）+ 尺码明细（有货码/缺货码）+ 价格（标价/实付/折扣名，若可得）+ 观测时间 + 深链 + "数据可信/延迟"标记。
- **必含免责提示**（P0，每条消息或群首条固定置顶）："按 X 分钟周期核对官方线上口径，非实时；到店前请先确认。"（见 §6.2）
- **失败处理**：通道失败自动重试 3 次（指数退避）；连续失败标记"通道不健康"并告警服务方 + 提示客户；邮件作为兜底通道同步一份。
- **可回执**：消息内提供"已抢到 / 无效"回执入口（钉钉/企微可用链接跳到只读页面完成，避免复杂交互）。

| 不可得 | 原因（有代码级证据） | 向客户的标准表达 | 替代方案 |
|---|---|---|---|
| **单店全量商品清单 / 商品总数**（"这个店一共多少件货"） | 微信云容器 + AWS API Gateway(SigV4) + CDN ACL 三重墙，纯接口不可达 | "这类数据不对第三方开放；我们提供的是**你关心的货号在 100 家店的逐店核对**，外加**每店活动专区预览（10 件）**。想要某家店到底有多少货，只能到店盘点。" | store/home 预览池（10 件/店）+ 关注货号探针 |

| 其他品牌数据 | 不在采集范围 | 明确告知不在服务范围 | 后续可评估扩展 |
| 实时性 | 刷新周期决定 | "按 X 分钟周期核对，不是实时；秒杀级抢购请以门店现场为准。" | 高档位缩短周期 |

**禁止用语（销售与界面文案）**："官方合作""Nike 授权""实时库存""全网最低价""保证有货"。统一替代："独立第三方门店信息核对服务""按 X 分钟周期核对官方线上口径"。

### 6.3 合规性说明（数据来源与边界）

- **采集方式**：仅使用服务方自有账号、经官方客户端 OAuth 流程获取的凭证，调用官方线上接口（与小程序同源）；不使用他人账号、不破解/伪造签名、不做 UI 抓取/OCR/模拟器。
- **不触碰个人数据**：不采集任何用户个人信息、聊天记录、支付信息；不代客户登录其账号；客户不需要提供任何凭证（对应硬约束 C2）。
- **数据性质**：所聚合的是**客户本可自行查询的公开商品与价格信息**（服务方代劳 + 定时化 + 历史化），不涉及商业秘密的窃取；但服务方应定位为"技术工具与信息聚合服务"，对商品真实可得性不作担保。
- **再分发限制**：客户仅限内部使用，不得转售原始数据、不得二次分发分享链接给非授权方（分享链接有有效期 + 可吊销）。
- **关系声明**：不宣称与 Nike 存在合作、代理或授权关系；合同与页面显著位置声明"独立第三方，非官方"。
- **服务连续性条款**：若上游接口变更或权利方提出要求，服务方可暂停/终止该功能并按剩余期限退费；对应 SLA 需写明"上游依赖型服务"的免责范围。
- **账号风控风险**：可能出现限流/冷却/封禁 → 服务方维持账号池与备用通道；客户无感（客户不承担也不接触）。
- **待办**：以上为需求方理解，正式对客协议与隐私政策需法务确认（见 §7）。

## 7. 开放问题（需用户拍板）

1. **定价与计费单位**：按月订阅 / 按货号 / 按店·轮包？是否提供 7 天试用（配额见 §4.3）？
2. **真实频率需求**：客户是否真需要"全国 100 店 × 每小时"？若多数只需"每天 2-4 次"，账号池可省一个量级（直接影响成本与套餐定价）。
3. **账号池规模与预算**：可接受维护多个 Nike 账号（每账号约 1,000–3,000 店·轮/天）吗？是否允许"共享账号池"（成本低）还是要求一客一账号（隔离好、成本高）？
4. **通知通道取舍**：是否投入微信服务号（企业认证 + 模板审核 + 订阅授权）？还是钉钉 + 企微 + 邮件 + 短信四条就够？
5. **开通方式**：客户自助注册开通 + 在线支付，还是全由服务方后台开（当前更贴合"零维护"）？
