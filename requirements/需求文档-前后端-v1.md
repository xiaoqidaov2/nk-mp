## 1. 项目概述

### 1.1 一句话定位

把现有「Nike 门店库存/价格监控」纯 API 能力（已实测：100 店清单、门店×尺码库存、门店价/促销、变化检测、上新）产品化为**面向 10-20 个客户的多租户 Web 平台**，服务方侧零人工维护（refresh_token 到期才需一次授权，≤1 次/账号/月）。

### 1.2 四条原始验收需求对照（对客承诺口径）

| # | 原始需求 | 现状能力 | 产品化后的承诺 |
|---|---|---|---|
| 1 | 找到所有商家 | ✅ 100 家门店清单（可刷新） | 「全部门店清单 + 地址 + 变更历史」 |
| 2 | 任意一商家的商品数量 | ⚠️ 全量清单纯接口不可达 | **不承诺**；替代：单店视图 = 已监控货号 + 满减专区预览池（10 件轮换），UI 强制标注「非全店清单」 |
| 3 | 指定货号哪些尺码有货 | ✅ 只读探针（门店×尺码，排除法） | 「全国 100 店 × 尺码级有货状态，附探测时间与可信度」 |
| 4 | 商品价格 | ✅ 标价/折扣/实付/促销名 | 「门店价 + 促销后实付价 + 促销名称」 |

### 1.3 不可动摇的硬约束（继承）

- **纯 API**：服务端调用，绝不占用/登录客户或任何人的微信客户端；无 adb/模拟器/Frida/OCR/截图
- **只读**：对 Nike 平台零写操作（cart_reviews 为只读审核，已验证购物车不变）——作为 CI 静态检查项
- **零人工**：客户零介入；服务方日常零人工，人工预算 ≤1 小时/月
- **数据真实性**：假阳性 0 容忍（宁可漏报标注「未探测」，不可错报「有货/无货」）

## 2. 需求分析：五方向交叉校验

### 2.1 五方向独立收敛出的关键事实（互相印证，可直接作为设计铁律）

| # | 事实 | 独立来源 | 设计含义 |
|---|---|---|---|
| F1 | **GTIN 是店级属性**（同货号在不同店可能是两套 GTIN/尺码集） | A（禁止跨店结构兜底）、C（尺码列取并集）、E（建模为 GtinStructure+StoreSku） | 唯一跨店键 = `(style_color, size_label)`；**禁止 GROUP BY gtin**；逐店取结构 |
| F2 | **价格条件可得**（仅"全可买且 ≤3 件"批次返回价格；无货时无价） | A（≤3 件迭代收缩）、E（price 可 NULL + price_confidence） | 价格列必须有「待补/陈旧」态；NULL→数值 不得当变价 |
| F3 | **可信度会翻转**（实测 3460 假阳性：空完成响应被当成"全有货"） | A（空完成响应不入库）、C（6 态语义，不可信≠无货）、E（trust/untrusted + 事件不参与状态机） | 全局引入可信度状态；**通知前必复验**（D） |
| F4 | **请求预算是总闸**（账号风控 + WAF + 时效的三角约束） | A（单货号全国扫描 0.5-1.2k 请求）、B（跨客户按店合并批次=核心杠杆）、D（60k TX/天硬闸） | 成本模型 = f(门店数×刷新频率×货号数)，按店合并是最优解 |
| F5 | **门店清单有重复**（storeCode 3875 同时以 `xian` 与 `NIKE0S08` 两个 regionId 出现） | C（99 唯一店号/3875 重复）、E（别名表） | Store 主键 = storeCode + regionId 别名表；否则 100 家算成 100+，扫两次、通知两次 |

### 2.2 冲突裁定（Rulings）

| # | 冲突 | 裁定 | 判错成本 |
|---|---|---|---|
| R1 | A 估「20 客户×20 货号/天 ≈20-50 万请求/天」 vs D 设「60k TX/天硬闸、单账号 ≤600 TX/h」 | **以 D 为准**：60k/天硬闸；A 的值是"全量全刷"的最坏值。日常监控走「关注店×关注码」小集合，全国扫描按需消耗配额；跨客户按店合并批次为一等杠杆 | 若客户真实需求是全员全店每日刷，则配额与定价需重算（见 §12-Q1） |
| R2 | 聚合参数不一致：B（聚合 60s、静默 60min）vs E（合并窗 300s、冷却 1800s） | **统一**：事件合并窗 300s（同店同类）、推送聚合 60s、同事件冷却 1800s、免打扰默认 22:00-08:00（租户可配） | 参数均可配置，改配置即可，无结构成本 |
| R3 | 价格主口径：标价 vs 实付 | **事件主口径 = 实付 total**；标价/折扣/促销名全量存储与展示；**仅促销名变化不告警**（仅记录）；跨店价格禁止比较 | 若客户实际关心标价波动，需增加"标价变化"事件开关 |
| R4 | 多账号池时机：A 建议提前 P0 vs D 给触发条件（>8000 TX/天 或 401≥2 次/周） | **v1 单账号 + 硬预算**；账号池列 P1，按 D 的触发条件启动 | 若单账号被风控封停，恢复需一次浏览器授权（≤1 次/月预算内） |
| R5 | L2 浏览器兜底（refresh_token 失效）部署在哪 | **服务端容器内置 Chromium**（Playwright），仍属纯 API 链路的授权环节，不触碰任何客户端 | 容器体积+~400MB；无 Chromium 则 refresh_token 到期后系统停摆 |
| R6 | 微信服务号/短信通知通道 | **P0 钉钉；P1 企微/邮件；P2 短信**；微信服务号不建议（无人值守不适用），以只读 Web + 钉钉替代 | 若客户强诉求微信内通知，需评估企微微信插件或订阅消息（成本/限制高） |
| R7 | 扫码查货 | **不做**（无 UPC→货号 映射接口）；批量导入用粘贴/剪贴板（兼容 `watch.txt` 逐行格式） | 无 |
| R8 | 不可达能力披露 | 单店全量清单/库存件数/成交价/实时性 **不得包装**；UI 标注 + 销售话术标准化（B-§6.2 已给话术与禁用词） | 合规风险与客诉风险，必须保留披露 |

### 2.3 数据质量红线（跨端强制契约）

1. 空完成响应（无 error 无明细）= **不可信**，禁止渲染为"无货"，禁止入库参与状态机
2. 状态六态：`有货 / 无货(INVENTORY_INSUFFICIENT) / 不售(PRODUCT_NOT_BUYABLE) / 未探测·不可信 / 有货待补价 / 该店无此货号结构`
3. 提醒前 100% 复验（消除 F3 类翻转）；UNKNOWN 不写基线
4. GTIN 结构 TTL ≤7 天；结构缺失禁止推断缺货
5. 所有观测/通知携带 `checkedAt` + 置信度；「实时」为禁用词，统一表述「最近探测」

## 5. 前端功能需求（摘要）

**IA 一级导航**：概览大盘 ｜ 监控任务（列表·4 步创建向导·任务详情/扫描进度）｜ 门店（单店·对比）｜ 货号（详情矩阵·批量查询）｜ 变化流水（+通知历史）｜ 通知（渠道·规则）｜ 配额与账户 ｜ 管理后台（客户·账号池·调度·数据源·审计）；顶栏常驻全局搜索 + **数据新鲜度徽标**。

**P0 页面**：概览大盘（今日变化+任务/账号健康）、监控任务列表、创建向导、任务详情/全国扫描进度、单店视图、货号×门店×尺码矩阵、变化流水、通知渠道+基础规则、配额用量。

**关键交互（C-§4）**：
- **全国扫描闭环**：批量粘贴 → 确认预计请求数与配额占比（无预估就显示"预估不可用"，不伪造 ETA）→ `[i/N]` 四类计数进度 → 断点续扫（明示复用范围）+ **仅重扫失败店** → 导出 → 一键转定时监控
- **矩阵筛选**：仅有货门店（默认开）/ 仅有货尺码 / 尺码区间 / 仅看促销 / 仅看变化 / 按有货码数或实付价排序 / hover 出价格与 `checkedAt`
- 提醒→深链：卡片 ≤8 行（长尺码折叠"41-44 共 5 码"）含探测时间与可信度，点开高亮单元格；数据已变则明确提示

**性能**（C-§6）：3000 单元格首屏 <1.5s、筛选 <300ms；进度用 SSE/WS 优先、2-3s 轮询回退；CSV 带 BOM、>5000 行异步导出；**前端不直连 Nike、不存 JWT**；客户角色不可见账号池/其他客户。

## 6. 数据模型（核心）

**19 实体**（E-§1）：Tenant / User / Account / QuotaUsage / SourceHealth / Store(+StoreRegionAlias) / Style / StyleSize / **GtinStructure** / **StoreSku** / ScanJob(+Failure) / **Observation**(+ObservationLatest) / RawResponseArchive / WatchTask / MonitorTarget / ChangeEvent / NotificationRule / Notification / OnlineListing。

**三条决定性建模事实**（E-§0）：F1 GTIN 店级 → `GtinStructure(结构哈希)+StoreSku`；F2 价格条件可得 → `price` 可 NULL + `price_confidence`；F3 可信度翻转 → `trust/untrusted_reason`、不可信观测不进状态机。

**存储策略**（E 容量结论）：不做全量逐轮入库（≈5.2 亿行/年不可接受）；**变更即写 + 每日全量快照 + ObservationLatest** ≈2400 万行/年；保留：报文 7 天 / 明细 90 天 / 事件永久 / 审计 180 天（D-§1.3）。

## 7. 变更检测与告警（摘要）

**事件 5 类**（E-§3）：RESTOCK（补货，款级升格 ≥2 码）｜SOLD_OUT（售罄；对 `EMPTY_COMPLETED/405/401/TLS_EOF/POLL_TIMEOUT/STRUCTURE_MISSING` **一律不触发**）｜PRICE_CHANGE（主口径实付；`discount` 0→>0 记 PROMO_START；仅促销名变化不告警；阈值 `max(¥1,1%)`）｜NEW_ARRIVAL_AT_STORE（`NOT_CARRIED→IN_STOCK`）｜SCAN_FAILED（9 个 error_code 与实测坑一一对应；失败率>20% 或连续 3 次才通知）。

**状态机前置**：`UNKNOWN/NOT_CARRIED/STRUCTURE_MISSING` 永不参与补货/售罄；`gap>max_gap` 视为基线失效只重建不提醒。

**聚合**：合并窗 300s、按店分组、跨店同款 ≥3 店合并、静默期顺延不丢弃、日上限折叠、`payload_hash` 幂等。

| R6 | 通知 P0 钉钉、P1 企微/邮件、P2 短信；不做微信服务号 | 微信内通知诉求需另评估 |
| R7 | 不做扫码（无映射接口），用粘贴导入 | 无 |
| R8 | 不可达能力强制披露（UI+话术） | 合规/客诉风险 |
| R9 | GTIN 按店建模；禁止 GROUP BY gtin / 跨店结构兜底；TTL≤7天 | 会误报（F1/F3 场景） |
| R10 | 门店主键 storeCode + regionId 别名表 | 重复扫描与重复通知（成本翻倍） |

## 12. 待用户拍板（附我的建议默认值）

1. **真实刷新频率需求**（决定配额与定价）：建议默认「关注货号×关注店」15-30 分钟级，全国扫描按需消耗配额
2. **SLA 是否合同化**：建议对外承诺"补货提醒 ≤30 分钟（99%）"，不承诺实时
3. **套餐定价与档位**（B-§4.3 五档）：建议先试用档 + 标准档两档起步
4. **备用账号归属**（服务方自有 vs 客户提供）：建议服务方自有（客户零介入）
